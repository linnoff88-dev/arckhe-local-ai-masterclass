🧩 Hardware categories

The AI hardware map: unified memory, VRAM, and bandwidth — and which category your machine fits into.

What it is:

Unified memory (Apple) combines RAM and VRAM in a single pool — it fits a huge model, but the lower bandwidth makes it slow. Dedicated VRAM (NVIDIA) has less memory, but much higher bandwidth and greater speed.

Why learn:

This trade-off determines everything: model size versus speed.

Key concepts:

Unified memory, VRAM, bandwidth.

What it is:

Mac Studio/Mac with lots of unified memory (e.g., 512 GB) can run models over 200 GB, but slowly.

Why learn:

Great for huge models; not ideal when you need speed.

Key concepts:

Apple Silicon, unified memory, large models.

What it is:

NVIDIA DGX Spark (~128 GB) and AMD Ryzen AI Max "Strix Halo": moderate memory and bandwidth.

Why learn:

Good balance between size and speed; the OS is usually Linux.

Key concepts:

DGX Spark, Strix Halo, balance.

What it is:

RTX 5090 (~32 GB, very fast) and RTX 6000 Pro (~96 GB, expensive). Fast, as long as the model fits in VRAM.

Why learn:

It's the choice when speed is the priority.

Key concepts:

RTX 5090, RTX 6000 Pro, dedicated VRAM.

What it is:

Mac mini, laptops, and PCs under $4k can run small models (Gemma, Phi, small Qwen models), embeddings, and classification.

Why learn:

It still delivers a lot of value—and it's where almost everyone starts.

Key concepts:

Small models, embeddings, low cost.

What it is:

macOS (usability), Linux (workstations), and Windows (gaming GPUs), each with pros and cons.

Why learn:

The OS affects drivers, runtimes, and day-to-day friction.

Key concepts:

macOS, Linux, Windows.

🎯 How to choose: what fits your machine

From use case to memory calculation: find the largest model your machine can handle — and how fast.

What it is:

Start with the use case (chat, code, RAG), not the hardware.

Why learn:

The use case determines the model range — and, from there, the required hardware.

Key concepts:

Use case, model range, requirements.

What it is:

GB ≈ (parameters in B) × (bytes per quantized weight) + context overhead. Table: 7B/13B/34B/70B × Q4/Q8/FP16.

Why learn:

Estimating before downloading avoids the frustrating "it didn't fit".

Key concepts:

Parameters, bytes per weight, overhead.

What it is:

Each hardware profile unlocks a different model range.

Why learn:

Knowing your ceiling keeps you from buying or downloading the wrong thing.

Key concepts:

VRAM, RAM, unified memory.

What it is:

tokens/s = how quickly the text comes out; memory bandwidth dominates here.

Why learn:

Sets what’s comfortable for chat versus batch processing.

Key concepts:

tokens/s, latency, bandwidth.

What it is:

A laptop + Ollama + a 3-8B Q4 model can run today, for free.

Why learn:

Removes the excuse, “I need to buy something before I can get started.”

Key concepts:

Zero cost, small model, Q4.

What it is:

Prioritize memory; use a dedicated GPU when speed matters; add multiple machines later (Tailscale, module 2.4).

Why learn:

Spending in the right order gets you much more for each dollar.

Key concepts:

Priority, dedicated GPU, multi-machine.

🧰 Operating system, drivers, and foundation

Get the groundwork ready: OS, drivers, and the layer that lets the GPU run AI — on macOS, Linux, and Windows.

What it is:

Every lab needs an up-to-date OS, disk space, and a terminal close at hand.

Why learn:

A solid foundation prevents 90% of the problems that come later.

Key concepts:

Updates, disk space, terminal.

What it is:

Apple Silicon uses Metal/MLX, with no extra driver; just install Homebrew.

Why learn:

It's the shortest path to getting a lab running on a Mac.

Key concepts:

Metal, MLX, Homebrew.

What it is:

CUDA is the layer that lets an NVIDIA GPU run AI; install the driver and check with nvidia-smi.

Why learn:

It's the most common setup for workstations and servers.

Key concepts:

CUDA, NVIDIA driver, nvidia-smi.

What it is:

GeForce driver + the WSL2 option for a Linux environment inside Windows.

Why learn:

Makes use of your gaming GPU without changing operating systems.

Key concepts:

GeForce, WSL2, Linux environment.

What it is:

The alternatives to CUDA and what actually works right now.

Why learn:

To realistically assess whether your AMD GPU is suitable for the lab.

Key concepts:

ROCm, MLX, alternatives.

What it is:

Organize model folders, version configs, and monitor temperature/power.

Why learn:

A clean lab scales; a messy lab leaves you stuck at the worst moment.

Key concepts:

Organization, versioning, monitoring.

🔗 Private network with Tailscale

Securely access your models from anywhere: a private network that connects your machines as if they were on the same LAN.

What it is:

Your machines are at home while you’re away — and opening ports to the internet is risky.

Why learn:

That's exactly the pain point Tailscale solves.

Key concepts:

Remote access, without opening ports or taking on risk.

What it is:

Point-to-point mesh VPN over WireGuard; creates a private network among your devices as if they were on the same LAN.

Why learn:

It's the piece that connects the whole lab in one place.

Key concepts:

Mesh VPN, WireGuard, tailnet.

What it is:

Install via script (curl ... | sh) and log in with sudo tailscale up; confirm with tailscale ip -4.

Why learn:

The setup is quick and identical on every machine.

Key concepts:

Installation, login, Tailscale IP.

What it is:

Expose Ollama on the tailnet (OLLAMA_HOST=0.0.0.0) and call it from another device using the 100.x IP.

Why learn:

This is how another machine starts using your model.

Key concepts:

OLLAMA_HOST, 100.x IP, tailnet.

What it is:

Tailscale app on your phone → use your home model from anywhere in the world.

Why learn:

It's the use case that unlocks real mobility.

Key concepts:

Mobile app, remote access, mobility.

What it is:

Principle of least privilege, MagicDNS, and basic ACLs; never expose it to the public internet.

Why learn:

Keeps the private network truly private.

Key concepts:

ACLs, MagicDNS, least privilege.
